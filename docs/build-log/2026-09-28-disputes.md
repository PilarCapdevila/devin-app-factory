## Decisions made without asking (product decisions)

1. Naming: permissions `disputes.dispute.read|work|decide|assign`, entity type `disputes.dispute`, approval action `disputes.decision`.
2. Final statuses `ACCEPTED` (we accept the chargeback) / `CHALLENGED` (fight approved); return → `IN_REVIEW`.
3. Due-soon threshold 72 hours; `dueState` (`overdue` / `due_soon` / `on_track` / `closed`) derived at read time, never stored; queue sorted by `respondBy` ascending; `?due=` filter.
4. Overdue disputes are flagged but can still be worked, proposed and decided — no automatic expiry status.
5. `evidenceSummary` (20–4000 chars) mandatory for `fight`, optional for `accept`; stored on the record, copied into the approval payload, kept on return so the analyst can revise.
6. PII = `cardholderName` + `customerEmail` only. `cardLast4` (4 digits) is not PII and is shown in clear. No full PAN anywhere (owner correction, see below).
7. Amount stored as integer minor units + ISO currency (EUR/GBP/USD in seed).
8. Reassignment only in `NEW`/`IN_REVIEW`; own `/api/disputes/analysts` route gated by `disputes.dispute.assign`.
9. Out of scope: submitting evidence to the card network/bank, evidence file uploads, deadline notifications, dispute creation UI (disputes arrive via seed only).
10. `support_agent` (refunds branch) gets no disputes permissions at rebase time.
11. Nav entry added via the existing `appNav` prop of `AppShell` from the authenticated layout (no `src/platform/ui` edit).

## Corrections / clarifications received

1. Plan approval came with one change from the product owner: **do not store full card numbers**. Dropped
   `cardNumber` from the model, migration, seed, `PII_FIELD_NAMES` and the planned `maskValue` suffix
   rule; store only `cardLast4` (String, 4 digits, not PII — same as the refunds app). Rationale: full
   PANs would put the system in PCI DSS scope and the queue only needs the last four. `cardholderName`
   and `customerEmail` remain PII (reveal field ∈ those two).
2. Process instructions from the orchestrator: follow the full playbook checklist, do not merge, and
   after opening the PR stop and wait — rebase onto `main` only after the refunds PR is confirmed merged.
